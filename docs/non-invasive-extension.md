# 不侵入式能力补全

> 这份文档是 qw-edit 项目（2026-09 ~ 2026-11）的方法沉淀。
> 项目本身已归档，因为官方把它做了。但下面这条路还可以用——**任何 Electron 客户端、「官方差一步」的需求，都是同一条路。**

## 一句话

**在不修改客户端本体、不重打包、不破坏代码签名、不动用户数据的前提下，把官方缺失的能力补上去。**

不是外挂，不是破解，不是替换安装包。是让客户端**用它自己的代码**去完成一个它已经有能力做、只是没做入口的动作。

## 判断能不能做：三个前置条件

动手之前先确认这三条，缺一条就别做：

1. **目标是 Electron / Chromium 壳**（或者任何带 DevTools 协议调试口的应用）；
2. **你要的能力，客户端内部已经有实现**，只是没暴露成 UI —— 这一条最关键。补一个入口是一回事，替客户端发明一套逻辑是另一回事，后者一定会破坏数据一致性；
3. **能力可以表达成"调用内部接口 + 补一个按钮"**，而不需要修改它的数据模型。

qw-edit 对上的就是第 2 条：官方一直有 `rollbackToMessage`（回退消息）、`deleteChat`、`forkFromMessage` 这些内部过程，只是没有把它们接到界面上。

## 四步

### 1 · 找到内部接口

解包 `app.asar` 读代码，找渲染层调用的 IPC / tRPC 路由表，确认**过程名 + 入参 + 返回结构**。

要点：

- 先确认过程**真的存在**（拿假 ID 调一次，看报"过程不存在"还是"参数错误"，两者含义完全不同）；
- 注意序列化包装（如 superjson 的 `{ json, meta }`），解包条件写错会静默拿到 `undefined`；
- 记录入参是否必填（如 `cwd`）、是否有软删除/硬删除两套语义。

### 2 · 打开调试通道

Chromium 的调试端口是**进程启动参数**，运行中无法事后开启；而 Electron 应用普遍是单实例（`requestSingleInstanceLock`），所以：

- 必须在启动那一刻就带上 `--remote-debugging-port=9222`；
- 已经跑起来的实例没法"补开"，只能重启 —— 这就是为什么这个方案需要一个后台小进程。

**这一环的产品礼仪很重要**：不要在用户不知情的时候杀掉他在用的客户端。用系统对话框问一句「功能尚未加载，需要重启客户端来加载吗？」——同意才重启，拒绝就本次不再打扰。用户对自己机器上发生什么有知情权。

### 3 · 注入脚本：调内部接口，不造数据

注入的脚本只有两个职责：

- **读**：通过内部接口读当前状态（会话、消息、上下文），别信 DOM；
- **写**：通过内部接口执行动作，让客户端的代码去改它自己的数据。

不要直接写 SQLite、不要直接改转录文件。一旦你绕过它自己的写入路径，就失去了它的事务、校验、事件广播 —— 出问题时你连"谁写坏的"都说不清。

### 4 · 挂界面：补入口，不抢主线程

界面入口用 DOM 挂载补。两条纪律：

- **不要定时全量扫描**。用 `MutationObserver` 观察变化 + `requestIdleCallback` 在空闲期执行。
  实测教训：定时轮询会和客户端的 React 重渲染互相撕 —— 它重画消息把按钮抹掉，你下一轮又重贴，每次重贴都触发一次布局，长会话滚动时炸出成倍的主线程阻塞（火焰图实测某个挂载函数独占 80% 非空闲时间）；
- **选择器要能扛版本**。优先用 `aria-label`、`data-*`、文本语义；不要依赖 Tailwind 生成的类名（`container/user-message` → `session-user` 这种改名一夜之间就能让全部按钮消失）。

## 三条不越的线

| 线 | 具体做法 |
|---|---|
| **不改客户端本体** | 不解包重打包、不改 `app.asar`、不动签名。这样客户端自动更新照常，你的东西不跟着坏 |
| **不动用户数据** | 不直接写库、不直接改文件。所有写操作走官方原语；原始文件保留作审计轨迹 |
| **不联网** | 工具自身不发起任何网络请求。唯一的连接是本机 `127.0.0.1` 调试端口 |

## 最容易做错的地方：假装成功

一个"看起来成了、其实没成"的实现，比没有这个功能更糟。qw-edit 踩过两个典型：

**假回退**：只截断了界面显示的消息（投影表），模型真正的上下文（会话转录）原封不动 —— 用户以为撤回了，模型却全都记得，重新生成时带着旧记忆作答。**这不是 bug，是骗人。**

**假输入**：客户端换成自定义富文本编辑器后，程序写进去的文本只是视觉假象，内部模型根本没收到 —— 点击发送无事发生。

对策：**宁可失败，也不要静默半成功**。

- 每一个写操作完成后，去**文件层或数据层**验证一次（行数、内容、指针），别只信返回值；
- 定位不到目标就停下来报错，不要"猜一个最像的"执行（重复文本、窗口化渲染下猜错就会作用到别的消息上）；
- 破坏性操作前二次确认，并把"会失去什么"讲清楚（"该消息之后的所有内容会被移除"而不是"确定吗？"）。

## 成本与退出条件

这套办法的代价是真实的，认了再动手：

- **安全面**：调试端口开着，本机任何程序都能连上控制客户端；
- **版本耦合**：DOM 结构、内部接口、数据形状，任何一处变动都可能让你的东西失效；
- **追不上**：官方一次迭代的投入，抵得上你几个月的追赶。

所以**一开始就要定退出条件**，并且写进 README：

> 官方原生支持了这个能力，本项目立即停止维护并归档。

qw-edit 就是这么结束的：2026-09-19 在反馈里写下这个期限，2026-11-25 官方 2.1.0 原生上线，项目归档。

## 什么时候值得做

- 需求**具体、克制**（补一个缺失的入口，而不是重做一个产品）；
- 官方**短期不会做**，而你现在每天都要用；
- 你能接受它**随时失效**，并且失效时不会损坏任何数据。

反过来，如果这件事官方下周就可能做、或者需要你替客户端发明业务逻辑 —— 别做。去提反馈，然后等。

**提反馈是有用的。** 这个项目的功能，最后是被官方实现的。
